## Session Startup

For a new substantive trading-project session:

1. Connect to the trading VPS.
2. Go to `/docker/trade-alerts`.
3. Check `git status`.
4. Pull with `git pull --ff-only` only if safe.
5. Read `RULES.md`.
6. Read only the relevant portion of `phases.md`.
7. Search `/docker/trade-brain` for relevant knowledge.
8. Read only the smallest useful set of notes.
9. Establish the appropriate test baseline before modifying code.

Do not reread everything before every command.

## Second Brain

Do NOT preload the entire `/docker/trade-brain` vault.

Search first using targeted filenames/terms. Open only relevant notes and follow `[[wikilinks]]` only when needed.

Current code/tests/config override vault notes for implementation truth.

Update the brain only when durable knowledge is established, such as:
- confirmed strategy definitions;
- validated findings;
- architecture decisions;
- important rejected approaches;
- durable API/data knowledge;
- important implementation rationale or pitfalls.

Do not save routine pytest output, temporary debugging, shell commands, or intermediate reasoning.

Follow `/docker/trade-brain/SCHEMA.md` when writing notes.

## phases.md

`phases.md` is the roadmap and progress tracker, not blanket authorization.

Before working on an unchecked item:
- verify it is genuinely unresolved;
- inspect existing implementation and tests;
- search the brain for relevant decisions;

Do not automatically advance into another major phase unless authorized.

## Trading Guardrails

Never:
- weaken/delete/skip valid tests just to make them pass;
- introduce look-ahead or future leakage;
- expose future session extrema;
- treat incomplete HTF bars as completed;
- silently alter session/time semantics;
- silently redefine wick-vs-close confirmation;
- silently redefine MSS, CHoCH, BOS, sweeps, FVGs, swings, entry timing, SL, or TP behavior;
- hide failures with broad exception handling;
- commit secrets or market datasets.

If two reasonable strategy interpretations would produce materially different trades, STOP and report the ambiguity.

## Engineering

Use the smallest correct change.

Preferred loop:
1. Reproduce.
2. Inspect relevant files only.
3. Run targeted test.
4. Make smallest justified fix.
5. Rerun targeted tests.
6. Run related/full suite when appropriate.
7. Update phases.md only after verification.
8. Update trade-brain only for durable knowledge.

Do not claim success without verification.

## Model Routing

Use the three-tier model system below.

### Tier 1 — flash-coder / DeepSeek V4 Flash

Prefer `flash-coder` for:
- routine Python implementation;
- straightforward pytest failures;
- well-specified unit or regression tests;
- small bug fixes;
- mechanical changes;
- simple configuration or fixture problems.

### Tier 2 — pro-coder / DeepSeek V4 Pro

Prefer `pro-coder` for:
- difficult Python engineering;
- cross-module debugging;
- complex test failures;
- substantial but clearly specified implementation;
- failures that Tier 1 could not resolve.

Escalate from Flash to Pro when the routine worker cannot confidently resolve the task.

### Tier 3 — default / GPT-5.6 Sol

The default profile is the supervisor and final authority for:
- planning and decomposition;
- look-ahead and causal-integrity questions;
- `as_of` semantics;
- session and trading-date semantics;
- incomplete higher-timeframe bar visibility;
- strategy definitions;
- MSS / CHoCH / BOS semantics;
- liquidity and sweep semantics;
- entry, SL, TP, and execution assumptions;
- major architecture decisions;
- genuine ambiguity;
- final verification of strategy-sensitive work.

If two reasonable interpretations could produce materially different trades,
STOP and request user guidance rather than inventing a rule.

### Concurrency

`/docker/trade-alerts` is one shared Git working tree.

Do not allow multiple code-modifying workers to edit it concurrently.

For implementation work:
1. run one worker;
2. verify its result;
3. escalate to the next tier only if necessary;
4. then continue.

Read-only investigation may be parallelized when safe.

Every worker result must still be verified by tests before a change is considered complete.

## Retry / Escalation Limit

Do not repeatedly attempt different fixes for the same underlying problem indefinitely.

For the same unresolved root cause:

1. Tier 1 may make one justified implementation attempt.
2. If it fails or remains uncertain, escalate to Tier 2.
3. Tier 2 may make one materially different justified attempt.
4. If the issue remains unresolved, escalate to Tier 3.
5. Tier 3 must block for human guidance if the issue is ambiguous or cannot be resolved confidently.

Do not cycle Flash -> Pro -> Flash on the same unresolved root cause.

A failed test must trigger diagnosis before another change. Do not use blind trial-and-error.

A retry is justified only when new evidence, a materially different diagnosis, or a clearly corrected implementation path exists.
